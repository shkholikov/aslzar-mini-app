# Токен бонусной карты: проверка на стороне 1С

В QR-коде мини-приложения вместо голого `clientId` теперь токен с ограниченным сроком действия.
1С проверяет его самостоятельно — обращений к нашему API не требуется.

Голый `clientId` (строка без точек) больше не принимается.

---

## Формат

```
00-00073809.1754301600.953329cd31b97995
└────┬────┘ └────┬───┘ └───────┬───────┘
  clientId    срок       подпись
              действия
```

| Часть | Что это |
|---|---|
| 1 | `clientId` |
| 2 | Срок действия, Unix-время (секунды) |
| 3 | Первые 16 символов HMAC-SHA256, hex в нижнем регистре |

Срок жизни токена — **5 минут**. Приложение обновляет его само, клиент всегда видит
действующий код.

---

## Проверка

**1. Разбить по точкам.** Не три части — отказать.

**2. Проверить срок.**

```bsl
ТекущийUnix = ТекущаяУниверсальнаяДата() - Дата(1970, 1, 1, 0, 0, 0);

Если Часть2 + 120 < ТекущийUnix Тогда
    // истёк, отказать
КонецЕсли;
```

120 секунд — допуск на расхождение часов.

**3. Проверить подпись.**

```
сообщение = Часть1 + "." + Часть2        // "00-00073809.1754301600"
подпись   = HMAC_SHA256(сообщение, КЛЮЧ)
```

Взять первые 16 символов и сравнить с `Часть3` без учёта регистра.

> **Ключ передаётся в HMAC как обычная строка (UTF-8), а не как hex.**
>
> Боевой ключ выглядит как 64 hex-символа, поэтому возникает соблазн сначала преобразовать
> его в 32 байта. **Этого делать не нужно** — в HMAC уходят все 64 символа как текст.
>
> Проверить себя можно так: если для токена
> `00-00073809.1786443757` с боевым ключом получается `2d4abd8075f38900` — значит ключ был
> декодирован из hex. Правильный результат: `2f0c638cb32d3287`.

Всё сошлось → берём `Часть1` как `clientId` и работаем как раньше.

---

## Время — важно

Наш сервер в UTC, ваш в Ташкенте (UTC+5). Unix-время от часового пояса не зависит, пересчитывать
ничего не нужно. Но:

**Использовать `ТекущаяУниверсальнаяДата()`, а не `ТекущаяДата()`.**

`ТекущаяДата()` вернёт местное время, результат будет больше на 18000 секунд, и все токены
будут выглядеть просроченными.

Если при отладке расхождение ровно ~5 часов — это оно. Если расхождение плавающее — уходят
часы сервера, нужен NTP.

## Тестовые векторы

Ключ тестовый, боевой передадим отдельно.

```
КЛЮЧ: test-secret-key-do-not-use
```

| Сообщение | Подпись (16 символов) |
|---|---|
| `00-00073809.1754301600` | `953329cd31b97995` |
| `00-00012345.1754301600` | `97c47c2123f71fdc` |
| `00-00099999.1900000000` | `c4f9767f1d8a62bd` |

Готовые токены для проверки:

```
00-00099999.1900000000.c4f9767f1d8a62bd    → принять (действует до 2030 г.)
00-00073809.1754301600.953329cd31b97995    → отклонить (истёк 04.08.2025)
00-00073809.9999999999.953329cd31b97995    → отклонить (подделка, подпись не сойдётся)
00-00073809                                 → отклонить (старый формат)
```

Совпали значения — реализация совместима.

## Ответы при отказе

| Причина | Сообщение кассиру |
|---|---|
| Срок истёк | «Код устарел — попросите клиента открыть приложение заново» |
| Подпись не совпала | «Недействительный код» |
| Не три части / старый формат | «Попросите клиента закрыть и заново открыть приложение» |

Первые два варианта важно отделить от третьего: карта не сломана, и в обоих случаях достаточно
попросить клиента обновить экран или заново открыть приложение. Старый формат будут показывать
клиенты, у которых Telegram закешировал предыдущую версию приложения — им нужно полностью
закрыть и открыть мини-приложение.

## Ключ

Ключ один. Передадим не через переписку — хранить в настройках базы, не в коде и не в отчётах.

При подозрении на утечку сообщите нам: выпустим новый, поменяем одновременно с двух сторон.

---

## Нужно от вас

1. Доступен ли **HMAC-SHA256** в вашей версии платформы. Если нет — сделаем проверку через
   наш API, криптография на вашей стороне тогда не понадобится.
2. Синхронизировано ли время сервера по **NTP**.
3. Сроки.
