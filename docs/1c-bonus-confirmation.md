# Подтверждение списания бонусов через Telegram

Документ для разработчиков 1С. Описывает, что нужно реализовать на стороне 1С и как
пользоваться нашим API.

## Проблема

Сейчас для списания бонусов на кассе достаточно знать `clientId` клиента. Этот номер —
обычный идентификатор для поиска, а не секрет: его видно в 1С, его можно было прочитать
под QR-кодом в мини-приложении, его легко переписать или сфотографировать.

В результате сотрудник, у которого оказался чужой `clientId`, может списать бонусы клиента
без его ведома. Такие случаи уже зафиксированы.

Со стороны мини-приложения мы уже убрали номер из-под QR-кода (версия 2.11.2), но это только
полумера: сотрудник с доступом к 1С всё равно может найти `clientId` любого клиента поиском.

**Закрыть дыру можно только на стороне 1С** — сделав присутствие клиента обязательным
условием списания, а не предположением.

## Решение

Перед списанием бонусов 1С отправляет клиенту в Telegram одноразовый код, клиент называет
его кассиру, кассир вводит код в 1С. Без верного кода документ списания не проводится.

Код генерирует и проверяет **сама 1С**. Наш API выступает только транспортом — мы код не
храним, не знаем и не проверяем. Ничего нового с нашей стороны разрабатывать не нужно,
эндпоинт уже работает в продакшене.

### Схема

```
Кассир: списать 150 000 бонусов
   ↓
1С: генерирует код 4 8 2 9 1 7, сохраняет его вместе с суммой и ID документа
   ↓
1С → POST https://api.aslzarbot.uz/v1/external/sendMessage
   ↓
Клиенту приходит сообщение в Telegram с суммой и кодом
   ↓
Клиент называет код кассиру, кассир вводит его в 1С
   ↓
1С сверяет код со своей записью → проводит документ
```

## API

### Эндпоинт

```
POST https://api.aslzarbot.uz/v1/external/sendMessage
Authorization: Bearer <api-ключ>
Content-Type: application/json
```

Документация со всеми кодами ошибок: **https://api.aslzarbot.uz/docs**

### Тело запроса

```json
{
  "phone": "998901234567",
  "text": "ASLZAR: 150 000 so'm bonus yechilmoqda.\nTasdiqlash kodi: 482917\nKod 5 daqiqa amal qiladi. Agar bu siz bo'lmasangiz, kodni hech kimga aytmang."
}
```

| Поле | Тип | Описание |
|---|---|---|
| `phone` | string | **Только цифры**, 7–15 символов. Без `+`, без пробелов, скобок и дефисов. |
| `text` | string | Текст сообщения, 1–4096 символов. |
| `parse_mode` | string | Необязательно: `HTML`, `MarkdownV2` или `Markdown`. |

> **Внимание — самая частая ошибка.** В 1С телефоны хранятся с префиксом `+`
> (`+998901234567`). Наш эндпоинт такой формат **не принимает** и вернёт `400`.
> Префикс и любые разделители нужно убрать перед отправкой: `998901234567`.

### Успешный ответ

```json
{ "ok": true, "result": { "message_id": 12345 } }
```

### Ошибки, которые нужно обработать

| HTTP | `error.code` | Что произошло | Что делать |
|---|---|---|---|
| 404 | `user_not_registered` | Клиента нет в нашей базе — он не запускал бота | Резервный сценарий (см. ниже) |
| 403 | `user_blocked_bot` | Клиент заблокировал бота | Резервный сценарий |
| 403 | `user_not_started` | Бот не может начать диалог первым | Резервный сценарий |
| 400 | `invalid_request` | Неверный формат тела запроса | Чаще всего — телефон с `+` |
| 429 | `rate_limited` | Превышен лимит запросов | Повторить через `retry_after` секунд |
| 502 | `telegram_unavailable` | Telegram временно недоступен | Повторить или резервный сценарий |

Лимит — **60 запросов в минуту** на один API-ключ.

## Обязательные требования к реализации

Эти четыре пункта — не рекомендации. Без них схема не работает.

**1. Проверка кода должна быть условием проведения документа, а не окном в интерфейсе.**
Если подтверждение реализовано как диалог, который кассир может закрыть или отменить, его
обойдут в первую же неделю. Проверку нужно встроить в логику проведения документа списания
бонусов.

**2. Резервный сценарий нужно определить до запуска.**
Часть клиентов не пользуется Telegram, кто-то заблокировал бота — ответы `404` и `403` будут
приходить регулярно. Если резервный сценарий это «пропустить подтверждение», вся защита
теряет смысл. Стандартное решение: подтверждение руководителем с обязательным указанием
причины, которая пишется в журнал. **Это самое вероятное место, где схема сломается на
практике.**

**3. В тексте сообщения должна быть сумма.**
Клиент должен подтверждать «списание 150 000 сум», а не абстрактное «подтвердите операцию».
Иначе он подтвердит любую сумму, не глядя.

**4. Свойства кода.**
6 цифр, одноразовый, срок жизни 3–5 минут, привязан к конкретному документу и сумме,
ограниченное число попыток ввода (например, 3). После успешного использования или истечения
срока код должен становиться недействительным.

## Доступ

Для 1С будет выпущен **отдельный API-ключ** — не тот, что используется другими интеграциями.
Это нужно, чтобы в журнале вызовов трафик 1С был отделим от остальных: журнал фиксирует
каждый вызов (телефон, статус, код ошибки, время) и служит независимым источником при
разборе спорных ситуаций.

Ключ передаётся в заголовке:

```
Authorization: Bearer ak_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Ключ секретный: не коммитить в репозиторий, не передавать в переписке, хранить в настройках
базы. Если ключ скомпрометирован — сообщите, мы его отключим и выпустим новый.
